Will this model run on your GPUs?

A quantized checkpoint can take an hour to download and still crash at load, return garbage, or run out of memory. quantpreflight reads the config and tensor headers, so you find out first. Enter a Hugging Face model or paste a config.json.

View the code

A pasted config stays in this tab. A model ID is fetched from Hugging Face.





































Why the failure comes so late


    

  1. You pull the weights
    A 40 to 400 GB checkpoint lands on your GPU nodes. That part goes fine, because nothing has looked inside it yet.
    2. 

  2. The engine starts loading
    Now vLLM or SGLang finds a tensor it can't split, a kernel your GPU doesn't have, or a token past the end of the embedding table.
    3. 

  3. You find out the hard way
    Sometimes it's a crash. Sometimes it's worse: the server runs and quietly returns nonsense.
    4. 




Everything it needs is in small JSON files and the first bytes of each weight file. A 38.74 GiB checkpoint took 887 KiB of reads.







What it checks


Each finding names the file or tensor at fault and how to fix it. Pasting a config.json skips the tensor checks. A model ID reads the tensor headers too, and the command line also handles GGUF, tokenizer.json, gated models, and local folders.

Run it on your model






Command line



quantpreflight check Qwen/Qwen2.5-7B-Instruct-AWQ --gpu H100 --tp 4







Pre-commit


repos:
  - repo: https://github.com/layer8labs8/quantpreflight
    rev: 
    hooks:
      - id: quantpreflight







GitHub Action


name: Model preflight
on: [push, pull_request]

permissions:
  contents: read

jobs:
  preflight:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: layer8labs8/quantpreflight@
        with:
          target: ./exported-checkpoint
          gpu: H100
          tp: "4"
          fail-on: high







It works on Hugging Face repo IDs, direct URLs, local folders, and single .safetensors or .gguf files. Set HF_TOKEN for gated models. The usage guide covers every option.







What it can't do


    

  • A clean report means no known problem was found. It doesn't prove the model will load or answer well.
    • 

  • It never reads weight values, so it can't see NaNs or measure quality loss.
    • 

  • The memory estimate assumes one request unless you pass --concurrency. Real traffic needs more.
    • 

  • Engines move fast. Its compatibility tables describe known behavior and can fall behind a new release.
